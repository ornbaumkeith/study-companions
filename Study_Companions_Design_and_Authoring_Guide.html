01 / How to reuse

Use one design system across different subjects

Study Companions is a family of standalone browser study tools. The reusable pattern combines structured explanation, retrieval practice, scenario questions, source documentation, and a deliberate review plan. Keep the shell consistent and replace the subject-specific curriculum and evidence.

  1. Attach a completed Study Companion as the visual and interaction reference.
  2. Fill in the project inputs in the master prompt: subject, audience, scope, version, official sources, work mode, counts, timer behavior, and filename.
  3. Use the design tokens and section contracts below. For a new implementation, use the normalized schema; for an existing file, preserve or explicitly migrate its actual schema.
  4. Build and verify the complete guide, then deliver its downloadable HTML.
Three kinds of guidance. Requirements summarize your requests. Reference implementation describes the four completed Esri guides. Future recommendations make the system easier to reuse; they are not claims that every current file already implements them.

This kit is an authoring specification with prompts, design tokens, and a data contract. It is not an installed AI skill, a finished companion for a new subject, or a replacement renderer for the four existing files. The small JSON example is explicitly synthetic.

Choose the work mode before editing

New

Create the curriculum and interface for a new subject. Verify its audience, scope, source policy, and any exam metadata.

UI only

Change presentation within scope. Preserve all study records, answer mappings, sources, features, and compatible progress.

Preserve and expand

Retain existing material and append verified additions. Recalculate operational totals and add clear context for retained legacy references.

If instructions simultaneously demand unchanged content and a larger curriculum, resolve the scope explicitly. Do not treat either instruction as permission to silently discard the other.

03 / Skills and responsibilities

The capabilities needed to build a companion

These are professional competencies and workflow responsibilities. They are tool-independent; the guide does not require a particular paid plugin, framework, or model.

SkillResponsibilityEvidence of good work
Subject-matter instructionExplain concepts, prerequisites, constraints, configuration decisions, and troubleshooting in plain English without losing precision.Accurate explanations with applicable versions, conditions, and direct sources.
Curriculum designMap objectives to domains, modules, Q&As, cards, questions, and exercises.Coverage map; no important objective omitted; depth matches the audience.
Technical researchRead authoritative sources and resolve contradictions or outdated guidance.Source register with title, URL, publisher, version, review date, and scope notes.
Assessment writingCreate one-best-answer scenarios with plausible distractors and diagnostic explanations.Four distinct options, one defensible best answer, and four source-backed rationales.
Study coachingTurn errors into a review plan and practical exercises.Specific blind spots, recall prompts, review actions, and a realistic timeline.
UI and interaction designKeep content discoverable, readable, consistent, and protected from accidental answer reveal.Clear section hierarchy, coherent controls, useful empty states, predictable navigation.
Front-end engineeringBuild a portable offline HTML application with reliable local state.No runtime dependencies; data-driven counts; stable IDs; working controls and import/export.
Accessibility and QACheck keyboard use, contrast, labels, reflow, scoring, timing, persistence, and preservation.Recorded checks and clear limits; no unsupported claim of certified accessibility or universal browser compatibility.

Reusable authoring sequence

Establish scope → verify evidence → map objectives → write content → review answers → apply the common interface → test behavior and preservation → deliver the files. Visual polish cannot compensate for incorrect study material, and accurate content still needs usable navigation and study controls.

Responsive behavior

  • At about 1100px, compact the sidebar toward 225px and reduce horizontal padding.
  • At 800px and below, switch to a 260px navigation drawer and a roughly 68px top bar. Keep theme accessible; move export/import/print into the drawer.
  • At 390px and below, stack hero actions and filters, let labels wrap, and retain readable body text.
  • Test 320px, 390px, tablet, desktop, and zoomed layouts. These breakpoints are reference choices, not proof that every content length will fit.
  • Long tables and URLs need local overflow/wrapping; the entire page should not scroll sideways because of them.

Accessibility acceptance targets

Use keyboard-operable native controls, a skip link, logical heading levels, visible focus, labeled inputs, meaningful selected state, and reduced-motion support. Do not communicate correctness, flags, or status solely through color. Manage focus when opening/closing a drawer and when moving to results.

For new companions, target at least 4.5:1 contrast for normal text and 3:1 for qualifying large text. W3C defines specific exceptions; do not infer compliance from the palette alone. W3C contrast guidance.

Make interactive targets comfortably usable. W3C’s minimum target criterion is 24 × 24 CSS pixels or an applicable exception, including sufficient spacing. A 44px control height is a useful design target for prominent touch actions, not a claim that all current controls use it. W3C target-size guidance. The completed guides were not certified as conformant through a full accessibility audit.

06 / Interaction contracts

Make the study loop predictable

Reading and recall

  • Keep module summaries and must-know rules visible enough to scan. Put long answers behind labeled disclosures.
  • Tell the learner to attempt the answer before revealing it. The control’s expanded state must be understandable with a keyboard and assistive technology.
  • Provide a clear no-results message when a search or filter returns nothing. Do not silently show an empty screen.
  • Save notes against stable question or module IDs. Distinguish a note from an answer or official source.
  • Source links should have descriptive names, open external documentation predictably, and identify relevant product versions.

Flashcards

  • Display “Front — Recall” and “Back — Answer,” or equivalent clear front/back labels.
  • Support click and keyboard flipping, previous/next, shuffle, know it, review again, and domain/status filters.
  • Keep ratings tied to card IDs, even after filtering or shuffling. Reset the visible position safely when the filtered set changes.
  • Handle an empty deck/filter result without undefined text or a broken counter. A card should test one coherent idea.
  • A source beside each card is the recommended normalized-template behavior; the retained EAEP card records do not carry the same per-card reference field as the other three files.

Practice and answer review

  • Display the attempt rules before starting: item count, duration, timer behavior, submission behavior, and treatment of unanswered items.
  • Selecting a choice should change selection state without revealing correctness. Group the four options as one accessible question.
  • On submission, calculate raw score and percentage from the actual item count; show domain-level feedback. Unanswered items score zero in the current pattern.
  • Explain each option independently. “Incorrect” by itself is not an explanation. Link the governing source near the rationale.
  • Reset only the attempt unless a broader reset is explicitly chosen. Preserve study notes and card ratings.
  • Confirm a premature reveal or replacement/reset action. Do not ask for repeated confirmation for ordinary navigation or answer selection.
  • Answers embedded in an offline file are visually hidden, not cryptographically protected. Do not market this as a secure proctored exam engine.

Timing must be explicit

The current Administration guide offers a pausable timer and resumes with timing paused after reopening. The other three guides use elapsed-time practice when timed mode is enabled: time away counts, and expiry is recognized when the page’s clock logic runs. A closed offline HTML page cannot execute a background submission. A future companion must choose a policy and describe it accurately.

Progress and print

Persist theme, completion, notes, card ratings, and attempt state locally when storage is available. Explain that this is browser/device-specific; it is not a synced account. Storage can be cleared or unavailable, and file-path/origin behavior must be tested in the intended browser. Offer export as a backup. Import must verify identity and compatibility before a confirmed replacement.

Print the intended section with readable light surfaces, useful source labels, and no navigation clutter. Expand study disclosures when printing them, then restore the previous reading state. Do not unlock the practice answer key merely because Print was selected.

07 / Curriculum and evidence

Build depth from objectives and documentation

Module contract

Each module needs a concise summary, must-know architectural patterns or conceptual rules, prerequisites, relevant limits/configurations, decision comparisons, common failure modes, and specific official resources. A module should teach an objective rather than merely collect links. Technical examples should identify the environment or assumptions that make the answer true.

Question-bank contract

The completed guides contain 100 deep Q&As, 100 flashcards, and 100 practice MCQs each. These are the reusable defaults for a full expanded companion, not a universal exam specification. New topics can use different requested totals. Do not fill a count with duplicates, invented details, or superficial paraphrases of the same item.

Technical Q&As should cover why, when, how, limits, and diagnostic choices. Flashcards should compress one retrievable idea. Practice questions should apply a rule to a realistic situation with enough constraints to make one answer best. All four distractor explanations should teach the decision boundary.

Evidence ruleRequired treatment
Official factsRead the specific authoritative page. Link the rule that supports the answer, not merely a vendor homepage.
Version baselineRecord the targeted edition/version. Label later guidance as supplemental when it differs from the exam or course baseline.
Documented caseIdentify the actual source case and its relevant conditions. Do not invent a scenario and call it an official documented case.
Original applicationClearly treat the scenario as an original educational application of documented behavior.
Conflicting documentationState the scope of the conflict, link both sources when relevant, and avoid asserting an unsupported universal rule.
Unknown exam detailLeave it unknown or omit the claim. Do not copy another exam’s count, duration, experience expectation, or passing score.
Copyright and integrityParaphrase explanations and link for deeper reading. Do not reproduce protected exam banks or whole manuals.
Scope exclusionsMark adjacent topics as context; do not present excluded tasks as confirmed tested objectives.

Official exam versus custom practice

In the four completed 2025 Esri guides, the official format is recorded as 75 questions in 105 minutes, while the custom bank has 100 questions and a 105-minute challenge. Those numbers are a historical reference for these files, not defaults for all credentials. The metadata model keeps officialExam separate from settings.practice.

For a new bank, use blueprint weights to guide coverage and clearly label any practice allocation. When retaining existing items, preserve them even if exact proportional counts become impossible. The current ESDP bank has 35/26/15/24 questions across its domains, while its displayed official weights are 35/26/14/25 percent.

Blind spots and the study plan

Cover common confusions, hidden prerequisites, version boundaries, limits, adjacent services, unsupported configurations, recovery steps, and cases where a successful command does not prove the whole workflow is healthy. Give a concrete next action for each blind spot: explain a distinction, reproduce a small scenario, inspect a setting, or consult a named source.

A reusable coaching sequence is: establish the baseline and prerequisites; complete high-priority modules; practise recall daily; run short hands-on exercises; attempt timed or untimed scenarios; review errors against documentation; retest with different scenarios. Set the duration to the learner’s schedule. Keep suggested timelines separate from official requirements, and do not equate memorizing a repeated bank with readiness.

09 / Recommended reusable schema

Separate content, presentation, and learner state

The kit provides Study_Companions_Content.schema.json, a new normalized authoring contract for future guides. It is validated as JSON Schema Draft 2020-12 and paired with a one-record synthetic example. Structural validation does not verify subject facts, source quality, or all cross-record relationships. Semantic checks beyond the JSON Schema

  1. Every ID is unique within its entity type. Every referenced source, domain, module, Q&A, and lab exists.
  2. A Q&A/practice item’s domain agrees with its module. Module Q&A lists and Q&A module IDs agree.
  3. Each practice item has exactly one A, B, C, and D option; its correct option exists; every explanation is nonempty and corresponds to the matching option.
  4. Actual bank lengths equal the configured targets. Displayed counts and score denominators come from those lengths.
  5. Official weights are not fabricated. If a complete percentage blueprint is supplied, check its total and document any rounding or practice-allocation differences.
  6. Actual source hosts and publishers satisfy the allowlist. A syntactically valid URL is not proof that it exists or supports the statement.
  7. When timerBehavior is none, duration is null; a timed mode needs a positive duration. Official-exam duration remains separate.
  8. Production material does not retain synthetic example content, fabricated official metadata, or unresolved placeholders.
  9. For updates, original records and source URLs survive unless a specific change is authorized. Track legitimate corrections separately.

Learner state is a separate document

The progress example contains companion/schema/content identity, export time, theme, completed module/lab IDs, notes, card ratings, and attempt state. The attempt records question and option order, selected answers by stable ID, flags, status, timing fields, and answer-key unlock state.

Content record: question-verification → correct option B
Learner state:  answers["question-verification"] = "B"

Never store an answer only as “row 17, index 1” if rows may be reordered.
Do not overwrite authored content with imported learner state.

Use a namespace such as study-companions:<companionId>:<schemaVersion>. Validate imported IDs and values, reject incompatible/cross-subject exports, and offer a clear backup before replacement. The new progress example is a recommended envelope, not a compatible import file for the current four guides.

10 / Implementation rules

Keep the delivered guide portable and maintainable

  • Deliver one HTML per subject with embedded CSS, JavaScript, and data. Build-time tools are optional; the learner must not need them.
  • Do not require CDNs, remote fonts, external JavaScript, a database, sign-in, telemetry, or paid services for study functions.
  • Use native semantic elements where possible: buttons for actions, links for navigation/resources, grouped radio options, labeled form controls, and details/summary for disclosures.
  • Render data and notes as text safely. Do not insert imported notes or source titles as executable markup. Embedded JSON must not be able to terminate its containing script element.
  • Keep external links descriptive and use rel="noopener noreferrer" when opening new tabs.
  • Handle unavailable storage and invalid imports without losing the active reading session. Do not describe browser storage as encrypted storage or a cloud account.
  • Use stable IDs and centralized count calculations. Avoid hardcoded “75,” “60,” “84 minutes,” or “four questions per module” in reusable UI logic.
  • Separate content versions from state schema versions. Adding curriculum can require resetting or migrating attempt state even when notes and card ratings remain compatible.
  • Prefer shared tokens and components for new guides. Avoid stacking more legacy override styles until mobile behavior becomes unpredictable.
  • Retain plain-text source records and a coverage map during authoring, so the finished content can be audited and reused.

Privacy and sharing

Sharing the HTML shares its authored content and embedded answer bank. Local browser progress normally remains on the learner’s device. A separately exported progress file may include private notes and answers, so label it clearly and let the learner choose when to share it. Do not embed your test notes or a learner’s personal progress into the released HTML.

Publication boundary

Creating a downloadable file does not publish it to GitHub or update a website. If publication is separately requested, verify the intended repository/page, replace the correct downloadable assets, update accurate page details and screenshots, and check the resulting public links. Never claim a deployment merely because a file was generated.

1. SCOPE AND PRESERVATION
Use the attached Study Companions reference and reusable specification as the design baseline. Keep the brand name “Study Companions.” Preserve the common layout, visual hierarchy, controls, and interaction conventions across subjects.

For NEW work, create the full requested content and interface. For UI-ONLY UPDATE, preserve all technical content, questions, correct answers, distractor explanations, source URLs, notes, study plans, functionality, and existing progress behavior. Do not add or remove curriculum. For PRESERVE-AND-EXPAND, retain every existing study record and add documented material to reach the requested totals. Update operational counts and labels to match the expanded bank. Flag factual conflicts with a source-backed annotation; do not silently rewrite retained content when preservation is required. Do not erase valid items to force an exact blueprint percentage. Report any resulting practice-allocation difference.

Do not make unrelated changes or publish to a website/repository unless separately requested. When updating, retain the exact filename requested by the user. Ask focused questions only for material missing information; do not invent a certification, version, audience, source policy, or missing attachment.

2. EVIDENCE AND EXAM ACCURACY
Use only the approved authoritative publishers for subject facts. For Esri subjects, use Esri documentation and resources; official Esri Community exam-information guides may establish blueprint details. For another subject, use that subject’s official publisher, standards body, or credential owner. Do not automatically carry Esri-only sourcing into an unrelated subject.

Open and inspect the specific sources supporting each material rule, configuration, limit, answer, or scenario. Prefer direct version-specific documentation over generic home pages. Record source title, URL, publisher, applicable version, and review date. Distinguish documented cases from original scenarios applying documented behavior. Never label an invented scenario as an official case. Identify unresolved or conflicting evidence rather than guessing. Do not mix current product behavior into an older exam baseline without labeling it as supplementary context.

Verify official exam name/code, objectives, weights, format, language, duration, question count, audience, and exclusions. Keep these facts separate from custom practice settings. The previous Esri guides used 100-question custom banks; that does not establish the length of any other official exam. Do not claim to reproduce confidential exam wording, actual questions, exact difficulty, or an undisclosed passing score. Write original scenario questions aligned to the public objectives. Paraphrase documentation; do not copy entire manuals or protected exam items.

3. REQUIRED CONTENT
Part 1 — Core guide and documentation map. Organize by major domains and modules. Each module needs a plain-English summary, must-know rules/patterns/configurations/limits, decision comparisons, prerequisites or failure modes where relevant, and direct official sources. Supply the requested number of technical Q&As. Every answer must resolve the question accurately and cite applicable documentation. Include troubleshooting, boundaries, and relevant documented scenarios.

Part 2 — Active-recall flashcards. Supply the requested number of cards. Each has Front: a focused question or concept, and Back: a concise accurate answer. Cover terminology, commands, configurations, metrics, diagnostic steps, prerequisites, and “when X versus Y” distinctions. Avoid cards that combine many unrelated facts. Associate cards with a domain and relevant source.

Part 3 — Practice questions. Supply the requested number of original, scenario-based, single-best-answer multiple-choice questions, with exactly four plausible options each. Use clear constraints that make one answer best. Avoid joke distractors, giveaway option length, predictable answer positions, and hidden assumptions. Each item needs a correct option and a separate explanation for all four options, with official references. Keep correct answers and explanations hidden during the attempt. Put Answer Key & Explanations in the final navigation section, unlocking after submission or an explicitly confirmed reveal if that mode is authorized. A downloadable offline HTML file cannot make its embedded answer data secret from someone inspecting its source.

Part 4 — Blind spots and study strategy. Include common pitfalls, easily confused distinctions, edge cases, prerequisites, adjacent topics clearly marked as such, practical exercises, and a realistic study sequence. Distinguish suggested study schedules from official exam requirements. Use missed-question patterns and weak domains to guide review; do not promise a passing score.

4. VISUAL SYSTEM
Style: modern, minimalist, high-contrast, professional executive workspace. Use calm spacing, clear hierarchy, thin borders, restrained rounded corners, and simple inline SVG line icons. Preserve the ClearWorth-inspired neutral foundation and restrained purple accents. Avoid dominant green surfaces, heavy gradients, ornamental clutter, stock dashboard decorations, excessive whitespace, and dated default-template styling.

Dark theme: background #0b0c0e, panel #151619, secondary panel #1d1e22, elevated panel #28292f, text #f1f1f3, muted text #b3b4bf, border #32333a, primary action #7541cc, purple accent #bb9bff, selected navigation #292335, restrained green links/success #8bd4b2.
Light theme: background #f5f5f7, panel #ffffff, secondary panel #f0f0f3, elevated panel #e5e5eb, text #202126, muted text #565963, border #d9dae1, primary action #6e3bbd, purple accent #6233ad, selected navigation #ede7f6, restrained green links/success #246a4c.

Use system-font fallbacks and no network-dependent fonts. Desktop baseline: approximately 252px sidebar, 76px top bar, main-content maximum 1480px, 32px vertical content padding, 22–52px responsive horizontal padding. Use 10–12px panel corners and approximately 6px buttons. Use readable long-form text; the reference baseline is 14px body text with 1.65 line-height. Do not shrink text to solve overflow.

Use these navigation sections in order: Overview; Study guide; Deep-dive Q&A; Flashcards; Practice exam; Blind spots & plan; Documentation; Answer key. Keep the toolbar for theme, Export progress, Import progress, and Print. On narrow screens, use a navigation drawer and place secondary toolbar actions inside it. Preserve keyboard access, visible focus, semantic headings, accessible labels, reduced-motion support, readable contrast, and responsive reflow. Treat accessibility requirements as acceptance criteria, not as a claim that conformance has already been certified.

5. INTERACTIONS AND ENGINEERING
Deliver one self-contained HTML file per subject, with embedded CSS, JavaScript, data, and necessary icons. No server, sign-in, runtime package installation, CDNs, external scripts, tracking, or paid services. Study content works offline; external documentation links require internet.

Provide domain filters and search where appropriate, collapsible answers, per-item notes, module completion, card flip/previous/next/shuffle/known/review-again, practice progress, submission/scoring, domain feedback, protected answer-key display, theme persistence, progress export/import, and print-friendly reading. Question flags/navigation are appropriate when using one-question-at-a-time practice. State exactly whether timing continues while away or pauses. Do not combine those behaviors under an ambiguous label.

Keep content separate from learner state. Use stable IDs and a unique storage namespace per companion and schema version. Derive all counts, percentages, numbering, and denominators from actual data. Validate imported progress for companion identity, schema version, types, item IDs, and option IDs before replacing local state. Confirm replacement and reset actions. Do not put executable HTML from notes or imports into the page. Handle unavailable browser storage with a clear notice and export option. Local progress is browser/device-specific and is not an encrypted account or cloud backup. Preserve or explicitly migrate compatible existing progress when updating; do not silently map old answers to different questions.

6. VALIDATION AND DELIVERY
Before delivery, verify exact totals, source references, unique stable IDs, four options and four explanations per MCQ, answer-key correctness, module/domain mapping, and source/version consistency. For updates, compare original records and URLs against the retained records. Check JavaScript syntax, DOM IDs, empty states, search/filter behavior, keyboard card flipping, scoring including the final question, unanswered-item handling, answer hiding before submission, timer expiration, reload persistence, progress export/import, themes, mobile navigation, print behavior, and offline opening. Test short and long content at desktop and narrow widths. Report any checks that could not be performed; do not claim a test passed without evidence.

Return the actual downloadable HTML file, not merely code pasted in chat or an inaccessible local URL. Briefly list its contents, how to open it, any custom-versus-official exam distinction, and material limitations. Make no further unrelated adjustments.
